# Quest skill design (QP-2815 / QP-2888)

Date: 2026-09-22
Status: design approved, not implemented
Classification: architectural

## 1. What this is

A new skill, `skills/quest-setup/`, that lets an agent drive the Xsolla Quest
Platform conversationally: create, list, view and edit quests, submit one quest
event, and verify that the event actually caused the quest to execute.

The skill is markdown only. It carries no executable code, matching every other
skill in this repository, and matching `docs/architecture.md`: "Skills call
Xsolla REST APIs directly."

## 2. Scope

### In v1

- Quest CRUD against qp-server.
- Event submission against qp-events-collector.
- Execution read-back against qp-data, for verification only.
- The full quest document the platform accepts: all 7 accepted node subtypes,
  the complete condition grammar, all 9 reward types including `web3_token`,
  activation limits, and branching connections.

### Out of v1

Three qp-server routes are deliberately excluded because they are machine or
internal-processing surfaces, not authoring:

- `GET /api/v2/quests/find-quests`
- `GET /api/v2/quests/find-quests-triggers`
- `GET /api/v2/quests/personalization/{user_id}`

The publisher-scoped family `/api/v2/quests/{publisher_id}/{id}` is documented in
`references/` as an existing alternative but is not the flow the skill drives. It
has update, delete and get, but no create and no list.

Everything else stays 1:1 with the platform. The guiding rule is that the skill's
ceiling equals the platform's ceiling: it must not invent capability the platform
lacks, and must not hide capability the platform has.

### Explicitly not in v1

The skill does not orchestrate Web3 payout. A `web3_token` reward is configured
on a quest node like any other reward. Settlement happens asynchronously inside
the platform. The skill never reads a transaction hash, never queries a wallet
balance, never calls the web3-minting-service, and never states that a token was
delivered.

  `qp-server/internal/http/validation/quest_config.go`,
  `lib/models/generic_quest/quest.go`, `node.go`, `condition.go`,

## 4. Architecture

### 4.1 Files

```
skills/quest-setup/
  SKILL.md
  references/
    quest-document.md
    node-subtypes.md
    conditions.md
    rewards.md
    events.md
    verification.md
    auth-and-environment.md
```

`SKILL.md` holds when to use it, prerequisites, the conversational flow, the
safety stops, and pointers. Target length around 200 lines, consistent with the
101 to 289 line range of the existing eight skills.

### 4.2 Source of truth

The single most important rule in the skill, because everything else depends on
it.

1. **Routes, path parameters, envelope field names and types, and top-level
   `required`** come from the **live OpenAPI document**, fetched once at the
   start of a session from the relevant service.
2. **Node subtypes, node `parameters`, the condition grammar, the 9 reward
   bodies, conditionally required fields, and every enum that OpenAPI renders as
   a bare `string`** come from `references/`.
3. On conflict, OpenAPI wins on shape and `references/` wins on rules.
   A `references/` rule that exists only in the hand-written Go validator must
   say so explicitly.
4. If neither source answers, the agent **asks the user**. It does not infer a
   field by analogy with another API.

Rule 4 is the testable form of the PRD requirement to ask for missing required
values instead of guessing.

### 4.3 Why the split exists

The OpenAPI documents are generated by huma from Go struct tags. They describe
the envelope correctly and then go silent exactly where an agent needs the most
help, because `Node.Parameters` and `IssueRewardParams.Body` are
`json.RawMessage` and the generator cannot see inside them.

Measured on the live stage document:

| Contract element | In OpenAPI | Actual source of truth |
|---|---|---|
| 27 routes, methods, path parameters | yes | matches |
| `Quest.required` = `name, type, status, created_by` | yes | matches the validator |
| `Node.required` = `id, name, type, subtype` | yes | matches |
| `Node.subtype` allowed values | **no**, bare `string` | 7 values in the validator |
| Condition grammar | **no schema at all** | `condition.go` |
| 9 reward bodies including `web3_token` | **no schema at all** | `issue_reward.go` |
| `start_date` / `end_date` required only when active | no | validator only |
| `nodes` minimum 2 when active | no | validator only |

There are also places where the struct tag actively disagrees with the validator.
The event payload tag says `oneof=global private within_project` while the
validator accepts five scope values, and the tag says `uuid4` while the rule
accepts any non-nil UUID. In each case the validator is what runs.
`references/` records these divergences by name.

### 4.4 Degraded mode

If a base URL is unreachable, which on these internal hosts usually means no
corporate network, the skill says so explicitly and offers to continue on
`references/` alone, stating that the envelope may have drifted. It never
continues silently, because an agent that cannot reach the schema will otherwise
state routes confidently and wrongly.

## 5. Environment and authentication

### 5.1 Variables

Two, both of which already exist elsewhere in this repository. No new variable
names are introduced, now or at cutover.

```bash
export XSOLLA_MERCHANT_ID=<merchant ID>        # already used by catalog-design, login-setup, login-styling
export XSOLLA_PROJECT_API_KEY=<project API key> # already used by catalog-design, login-setup
```

These are sent as `Authorization: Basic base64(merchant_id:api_key)`, which is
the credential shape QP-2858 specifies.

No base-URL variable is introduced. No skill in this repository has one; hosts
are written literally in the skill text. No `XSOLLA_ENV` either: v1 targets stage
only, so a selector would select nothing. Both are added when a second
environment actually exists.

### 5.2 Hosts

```
stage  qp-server            https://qp-server.nl-k8s-stage.srv.local
stage  qp-events-collector  https://qp-events-collector.nl-k8s-stage.srv.local
stage  qp-data              https://qp-data.nl-k8s-stage.srv.local
```

All three are internal. The skill states this in prerequisites rather than
letting the user discover it through a timeout.

### 5.3 The auth window

`Authorization: Basic` is **not accepted yet**. On `origin/dev`, the qp-server
authenticator recognises only `Authorization: Bearer` and `X-REQUEST-APIKEY`, so
a Basic credential produces a "no credential" 401. On the unmerged auth branch a
`MerchantKeyVerifier` exists but is a stub that logs
`verify_merchant_key.unimplemented` and always returns 401 "Merchant API key
authentication is not yet supported".

The implementation is planned as **QP-2862, inside QP-2858 Phase 3**, which is To
Do, unassigned, and explicitly depends on Phase 1 (QP-2851, in progress, unmerged)
and Phase 2 (QP-2852, To Do).

The approved decision is to **write the skill against the target Basic contract
only and wait for QP-2862**. No temporary credential variable is introduced.

Consequences, accepted deliberately:

- QP-2889, temporary stage authentication, becomes unnecessary and should be
  closed.
- QP-2894, the installation-to-Backpack demo, is blocked on Phases 1, 2 and 3.
- QP-2892, stage ERC-20 validation, is blocked on the same.
- Write-path agent tests cannot run until QP-2862 lands. Read-path tests can run
  today, see section 10.

### 5.4 The seam

The header, the credential and the scope resolution are named in exactly one
file, `references/auth-and-environment.md`. Every other file and every step in
`SKILL.md` says "an authenticated QP request" and restates neither the header nor
the variable names.

The honest limit of this seam: it bounds the blast radius, it does not guarantee a
one-file change. Phase 3 may introduce publisher-facing routes, since QP-2860 is
titled "Project scope resolution". `auth-and-environment.md` therefore carries an
"incoming changes" section naming the open merge requests, and the cutover work
begins by re-reading the deployed contract rather than by editing to a plan.

### 5.5 Route family

The skill drives the **scopeless** family, `/api/v2/quests`, where the scope is
resolved from the credential. Both unmerged auth stacks keep both route families
unchanged, so this is the shape most likely to survive.

Discipline is preserved not by putting an account UUID in the path but by a rule:
**before the first write, the skill reads back and displays the scope it landed
in**, using the `account_id`, `publisher_id` and `project_id` on returned quests,
and asks for confirmation. The account-scoped family
`/api/v2/accounts/{account_id}/quests` remains available as an explicit override
when the user names an account.

This decision is **provisional**. If Phase 3 introduces project-scoped
publisher-facing routes, the skill switches to them and picks up
`XSOLLA_PROJECT_ID`, which is also an existing repository variable.

## 6. The quest contract the skill must know

A quest is a graph, not a flat object. This is the single fact that shapes the
whole conversational flow.

- The create body is the full quest document: `nodes[]` plus `connections`, a map
  from a node UUID to a list of edges.
- A quest with `status: active` requires at least 2 nodes and a connection graph
  that is referentially valid and acyclic.
- A quest with `status: inactive` requires almost nothing: `name`, `type`,
  `status`, `created_by`.
- There is no PATCH. Update is a full-document PUT.
- `status: deleted` exists as a value but is not accepted on write.
- Node subtype `event_check` is declared as a constant but is **absent from the
  accepted-subtype list**, so a node using it is rejected. `references/` records
  this trap by name, because an agent reading only the enum will fall into it.
- Accepted subtypes are `date_and_time`, `dynamic_event`, `issue_reward`,
  `send_xsolla_app_notification`, `send_http_webhook`, `custom_attributes_check`,
  `webshop_personalization`.
- Reward types are `xsolla_points`, `virtual_currency`, `loyalty_points`,
  `lootbox`, `custom`, `inventory_item`, `vc_wallet_ticket`, `web3_item`,
  `web3_token`.
- `web3_token` body is `item_sku` (required, string) and `amount` (required,
  float greater than zero, whole tokens rather than base units).

Event submission is a **different service** with a different contract. Required
fields are `idempotency_key` (a non-nil UUID), `name`, `user_ids` (at least one
typed identifier) and `client_timestamp` (RFC3339). The account is not in the
body; it is derived from the credential.

### 6.1 Confirmed reference shape

A real stage quest, re-fetched from qp-data on 2026-09-22, confirms the minimal
two-node shape the validator implies:

- quest `WEB3 Token ERC-20 Stage Test`, type `liveops`, status `active`
- trigger listens for the event name `web3.token_test`, so the trigger subtype is
  `dynamic_event`
- one `issue_reward` action, `type: web3_token`, `purpose: quest_completion`,
  body `item_sku: XLA-000-001`, `amount: 0.01`
- `conditionEvals` empty, so there is no condition node
- two executions with status `COMPLETED`, both dated 2026-08-24

This is evidence that the path worked a month ago on stage. It is not evidence
that it works today, and it is not a production-readiness claim.

## 7. Conversational flow

The staircase follows the validator: an inactive quest is cheap to create, so the
conversation builds a draft and fills it in rather than demanding a whole graph up
front.

1. **Bring-up.** Fetch the OpenAPI documents. Check the credential is present.
   List quests and display the resolved scope. Confirm with the user.

   Until QP-2862 lands, this step fails at the first qp-server call with a 401,
   because the Basic lane is not accepted yet. The skill must say exactly that,
   naming the ticket, rather than reporting a generic authentication failure.
   The qp-data path in step 7 continues to work, because it needs no credential.
2. **Draft.** Create the quest as `inactive` with the four required fields. It is
   already a valid object to keep talking about.
3. **Fill in.** Add nodes and edges one at a time, asking for each missing
   required value rather than guessing. Show the assembled document before
   sending.
4. **Activate.** A separate step: move to `active` with dates, after checking
   there are at least two nodes and the graph is acyclic.
5. **Edit.** GET, mutate, full PUT. The skill warns that PUT replaces the whole
   document.
6. **Event.** Build the payload, generate a UUID `idempotency_key`, set an RFC3339
   `client_timestamp`, submit to the collector.
7. **Verify.** Read `GET /api/v1/quest-executions` from qp-data and report what
   actually happened. See section 9.

## 8. Safety stops

- Confirm the resolved scope before the first write.
- **Separate, explicit confirmation before activating a quest that contains an
  `issue_reward` node.** Activation means real payouts.
- Confirm before submitting an event.
- **After an uncertain event response, such as a timeout, do not resend, neither
  with the same idempotency key nor with a new one.** A timeout is not a failure.
  The skill reports "result unknown" and stops.
- Never claim a reward was delivered. Settlement is asynchronous, and a successful
  event response says nothing about payout.

## 9. Verification through qp-data

qp-data is a read-only service on stage that currently requires no credential.
`GET /api/v1/quest-executions` accepts `questId`, `userId`, `accountId`,
`publisherId`, `status` and paging, and returns per-execution status plus the
status of each action node.

This lets the skill separate three claims that were previously conflated:

1. the event was accepted by the collector,
2. the quest executed and the `issue_reward` node completed,
3. the token reached the wallet.

The skill can assert 1 and 2 from evidence. It never asserts 3.

qp-data is used **for verification only**. Listing and viewing quests stay on
qp-server, so there is exactly one way to perform each operation.

Note for the platform team, outside this skill's scope: qp-data on stage returns
account names, user `xsollaId` values and reward configuration with no
authentication. The host is internal, but the absence of auth is worth a
deliberate review.

## 10. Error handling

Branch on HTTP status only. There are no stable machine-readable error codes.

| Status | What the skill says |
|---|---|
| 401 | missing or invalid credential |
| 403 | insufficient capability for the required `questconfig:*` |
| 404 | "not found, or no access, or the project is not onboarded to QP" |
| 409 | conflict |
| 422 | validation failed; `detail` is shown verbatim |
| 5xx | server error; retry reads only |

Two body shapes exist. Middleware failures return `{"error": "..."}`. Handler and
service failures return RFC 7807 `application/problem+json`. In the 422 case the
`errors[]` array is **not** populated: per-field messages are flattened into one
`detail` string joined with `"; "`. Those `location: message` pairs may be parsed
for display to a human, never for control flow.

## 11. Testing and acceptance

The auth window splits testing by direction rather than by date.

| Surface | Testable today |
|---|---|
| qp-data reads: quests, quest-executions, metrics | **yes, no credential needed** |
| qp-server writes and event submission | no, blocked on QP-2862 |

- **Live read-only agent test, now.** The agent is asked to find and describe the
  stage quest and its executions through qp-data, and the transcript goes in the
  PR. This satisfies the repository rule that a PR includes an agent test with the
  exact prompt and a one-line result.
- **Offline contract conformance, now.** The agent assembles a quest document and
  an event payload through the conversational flow, and the output is validated
  against the live OpenAPI schema and the documented validator rules **without
  sending**. This covers the write path's content while the write path's
  credential is unavailable.
- **One live write test**, queued for when QP-2862 lands.

### 12.1 Validator noise

`validate_skills.py` walks all of `docs/**` on the filesystem, ignoring
gitignore. The research reports under `docs/superpowers/qp-2815/` currently
produce 136 errors, all of the form "broken relative link", because they cite
source locations as absolute paths like `/Users/.../web3_api.go:175` and the
validator reads those as relative links.

Resolution: move the research reports out of the repository tree. They are
gitignored, they are never published, and their only effect inside the tree is to
hide real errors behind false ones. Changing a shared validator to accommodate
private drafts would be the wrong fix.

## 13. Merge preconditions

v1 is an internal draft on a branch. Before it can merge to the public
repository:

- The internal `.srv.local` hostnames in `references/auth-and-environment.md`
  must be reviewed. Publishing internal topology is a disclosure decision, not an

- QP-2862 must have landed, otherwise the skill cannot work for anyone outside.
- The `quests` domain addition needs sign-off from the repository owner.

## 14. Open items

1. **Phase 3 route shape.** QP-2860, "Project scope resolution", may add
   publisher-facing routes. The scopeless-route decision in 5.5 is provisional
   until Phase 3 is deployed and re-read.
2. **Uniform 404.** Phase 3 makes unknown, un-onboarded and unauthorized projects
   return byte-identical 404s on purpose, to avoid turning the endpoint into an
   oracle over QP's customer list. The skill must never report a 404 as "it does
   not exist". The wording is "not found, or no access, or the project is not
   onboarded to QP".
3. **`ID 0` is valid** for both merchant and project identifiers and must never be
   treated as an absence sentinel.
4. **Conflicting auth stacks.** No branch contains both `Principal.Source` and
   `Principal.Owner{Kind,ID}`; they are competing reshapes of the same struct and
   one deletes `HomeAcct`. Which one lands changes how scope resolves for a
   scopeless request.
5. **Reward fixture freshness.** The confirmed `XLA-000-001` / `0.01` fixture last
   executed on 2026-08-24. A fresh rehearsal is required before any demo.
